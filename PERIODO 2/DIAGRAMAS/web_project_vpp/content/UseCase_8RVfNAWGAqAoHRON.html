Use Case Note
■ Workflow //FLUJO DE TRABAJO
    • Intenta iniciar la reserva de un servicio desde la aplicación o plataforma web (RF09).
    • El sistema verifica de forma previa el estado del perfil en la base de datos.
    • Al detectar la sanción activa, interrumpe el flujo de reserva antes de la selección de horario y despliega una pantalla de bloqueo con la fecha de rehabilitación de la cuenta.
■ Business Logic //LOGICA DE NEGOCIO
    • La validación de bloqueo se ejecuta en el paso 1 del flujo de reserva para evitar consumo innecesario de recursos o selecciones parciales en la agenda.
    • El bloqueo aplica para reservas en línea autorreferenciadas. Las excepciones manualmente autorizadas por el Dueño requieren registro explícito de motivo en el log de auditoría.
    • Una vez alcanzada la fecha y hora de finalización de la sanción, el sistema remueve el estado de bloqueo de forma transparente sin intervención manual.
■ Decisions //DECISIONES
    • Si el cliente intenta omitir el bloqueo creando una cuenta secundaria con los mismos datos de contacto (teléfono/correo), el sistema identificará la coincidencia e impondrá el bloqueo sobre el nuevo registro.

(INTERCEPTACIÓN DE INTENTO DE RESERVA CON SANCIÓN ACTIVA)
Steps
1. El Cliente navega por la plataforma, selecciona un establecimiento, elige un servicio y presiona la opción "Agendar Cita / Reservar".
2. El sistema intercepta la solicitud y valida el estado de la cuenta del usuario consultando el registro de penalizaciones.
3. El sistema evalúa el estado del perfil respecto a sanciones automáticas o manuales:
    3.1. if el usuario se encuentra con el estado de sanción Activo en la base de datos:
        3.1.1. El sistema deshabilita inmediatamente el botón de confirmación de reserva y bloquea la selección de franjas horarias en la agenda del barbero
        3.1.2. El sistema despliega un modal emergente de bloqueo con la restricción: "Operación No Permitida. Tu cuenta se encuentra temporalmente restringida para realizar nuevas reservas debido a la acumulación de cancelaciones
        3.1.3. El sistema presenta en pantalla los detalles del bloqueo consultados del perfil (RF42): Fecha de inicio, motivo de la sanción y fecha exacta de liberación.
        3.1.4. El sistema frena la creación del registro en la tabla de citas y retorna al cliente a la pantalla principal o al perfil de usuario
    3.2. else if
        3.2.1. El sistema permite al cliente seleccionar la fecha/hora deseada y procede con el flujo normal de creación y confirmación de la reserva
         end if

(INTENTO DE RESERVA POR MÉTODOS ALTERNOS O DIRECTOS)
Steps
1. El Cliente intenta enviar una solicitud de reserva mediante un enlace directo de agendamiento, escaneo de código QR de la sede o un endpoint directo de la API.
2. El sistema valida las credenciales y el token de sesión del usuario.
3. El sistema evalúa si existe un registro de sanción vigente para la cuenta:
    3.1. if la fecha y hora actual es menor a la fecha de finalización de la sanción almacenada en el sistema:
        3.1.1. El sistema rechaza la petición HTTP con un código de error de restricción de negocio
        3.1.2. El sistema notifica en la interfaz o respuesta JSON: "Acceso denegado: Usuario bloqueado por sanción hasta el [Fecha fin de sanción]".
    3.2. else if
        3.2.1. El sistema delega la ejecución al módulo de reservas (RF10) para procesar la cita.
         end if
